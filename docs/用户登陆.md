# MacroTracker 用户登录与多人使用方案

2026-10-19

状态：改为本站自管用户名密码登录，功能代码、本地自动化测试和本地浏览器主流程已完成，尚未上线。进度见 [任务清单](用户登陆-tasks.md)，配置见 [部署配置](用户登陆-部署配置.md)。

## 原始想法

以下保留最初的想法，具体实施范围以本文后续章节为准。

我给朋友分享这个MacroTracker后，他们表示想要使用，但是原本是我打算自己用的，所以在deploy到Cloudflare时只是通过输入访问密钥来访问。

我打算做一个登陆页面，就是也要以游戏风格的创建自己的角色，比如登陆的用户名，密码等。注册好后，才到创建角色，输入身高体重，性别，职业，目标。年龄，药水补给等，完成后才进入页面。

然后我还要多加一个/admin 的页面，用来做管理（需要输入问密钥来access这个admin path，然后才进入输入username password登陆）。比如用户管理（列出用户），level的经验管理，音效管理，星星获得管理，还有任何可以转成amdin管理且我没有提到的都可以推荐我。

然后因为我是用免费Cloudflare部署的，看下有没有必要做一些用户的限制，比如可能用的数据太多，可以考虑做比如google email那个googled drive显示目前可以用多少，X GB of X GB used等，这个我是有考虑到，你可以看下有没有必要，因为不确定Cloudflare那边的数据库有没有limit或者超过了需要付费等。

## 已确认方向

- 管理员在后台生成邀请链接分享给朋友，朋友打开链接注册，不开放无邀请注册。
- 本站自管用户名密码，登录用户名与可修改的角色昵称分开。
- 坚持 Cloudflare 免费方案，不购买 Workers Paid。
- 注册后完成 RPG 风格的角色创建，再进入日记。中途退出后，下次登录继续填写。
- 身高、体重、年龄、性别、职业、目标体重、药水补给复用现有设置。职业仍对应日常活动量，药水补给仍对应每日饮水目标。
- 沿用现有目标体重和营养计算，不新增减脂、维持、增肌模式，也不另做职业技能系统。
- 提供退出登录、修改密码和管理员重置临时密码的流程，第一版不依赖邮件服务。
- 后台管理全站经验和星星获得规则，不提供针对个人手动增减奖励的功能。
- 继续使用现有 Cloudflare Pages Functions + D1、原生 ES modules 和无构建部署方式。

## 多用户数据与账号边界

原版本使用共享访问密钥，个人设置固定为 `id = 1`，各业务表没有账号归属。新版通过 `0007_accounts.sql` 引入账号归属，业务 API 改为 Cookie 会话。迁移尚未在生产执行。

- 个人设置、食物仓库、饮食、饮水、体重、成就、碳循环配置和日程均归属账号。
- 服务器从登录会话确定用户，不信任请求中自行指定的用户身份。所有查询、修改、删除和关联更新都必须检查归属。
- 日期、成就编号等唯一约束按用户隔离；查询索引包含用户维度。存档中重复的记录编号也不能覆盖其他账号的数据。
- 导入与导出只处理当前账号的业务数据，不包含密码、会话、邀请码或管理员配置。覆盖导入保留事务完整性和失败时不破坏旧数据的行为。
- 现有个人数据全部迁入所有者账号。新用户不得继承所有者的身体资料和历史记录；默认食物使用独立副本，避免互相修改。
- 退出、会话失效和切换账号时清理旧页面状态，升级提示等与个人进度相关的本地记录按账号区分。
- 迁移前备份并在本地副本演练，使用新编号迁移文件，不修改已应用的迁移。上线步骤必须覆盖旧共享密钥入口停用、所有者及管理员初始化和恢复方式。

核心验收：A 用户即使知道 B 的记录编号，也无法读取、修改或删除 B 的数据；A 导入存档不能影响 B。

## 管理后台

`/admin` 使用普通登录会话：已登录的管理员可直接进入，未登录时显示管理员登录表单，普通账号返回 403。页面和管理 API 均在服务端检查有效会话及管理员角色，不再要求额外密钥或 30 分钟二次授权。管理密钥仍用于所有者的一次性认领。

| 功能 | 范围 |
| --- | --- |
| 用户管理 | 用户列表、停用、恢复、密码重置；默认不展示私人饮食和身体记录 |
| 邀请码管理 | 生成、限制使用次数、停用；并发注册也不能超额使用 |
| 关键操作记录 | 记录管理员、操作时间、对象和变更内容；不保存密码、原始会话或重置凭证 |
| 全站经验规则 | 配置现有经验来源和升级规则中的有限数值，不做任意公式编辑器 |
| 全站星星规则 | 配置现有获得条件，保持最多三颗星的现有展示结构 |

停用账号后，其已有会话也必须失效。管理员重置临时密码时同时撤销该用户的旧会话。

### 规则修改与历史记录

当前经验和星星根据历史记录重新计算，已解锁成就则永久保留。此次沿用这一行为：后台修改全站规则后，历史经验、等级和星星可发生变化，已经解锁的成就不撤销。

保存前明确提示影响并展示修改内容，保存后记录操作。规则必须有服务端校验，用户端采用同一份有效配置。第一版不实现“仅对未来生效”的规则版本或奖励流水。

## 免费资源与使用限制

以下为 2026-10-19 核对的官方免费额度，不代表本项目的实际使用量，也不代表可承载用户数的测量结果。

| 资源 | 免费额度 | 来源 |
| --- | --- | --- |
| 单个 D1 数据库 | 500 MB | [D1 限制](https://developers.cloudflare.com/d1/platform/limits/) |
| 账号全部 D1 数据库合计 | 5 GB | [D1 限制](https://developers.cloudflare.com/d1/platform/limits/) |
| D1 读取行数 | 每天 500 万行 | [D1 计费](https://developers.cloudflare.com/d1/platform/pricing/) |
| D1 写入行数 | 每天 10 万行 | [D1 计费](https://developers.cloudflare.com/d1/platform/pricing/) |
| Pages Functions 与 Workers 请求 | 合计每天 10 万次 | [Pages Functions 计费](https://developers.cloudflare.com/pages/functions/pricing/) |
| Workers 每次 HTTP 请求 CPU 时间 | 10 ms | [Workers 限制](https://developers.cloudflare.com/workers/platform/limits/) |

目前项目绑定一个 D1 数据库，应先关注 500 MB 上限。D1 免费读写额度用尽后查询会报错，存储额度用尽后无法继续新增相关数据或结构；不会自动以付费额度继续执行。日额度在 UTC 00:00 重置。升级付费计划后的超额计费应另行评估，不能把免费计划的行为套用于付费计划。

现有 `/api/state` 会一次读取全部历史。D1 按扫描行数计量，并非仅按返回结果数量计量，所以用户维度索引与历史读取成本比用户容量条更值得优先关注。

- 通过邀请码控制内测规模，对认证和异常写入设置合理频率限制，对存档导入设置大小及记录数边界；具体数值由验证任务确定。
- 先在 Cloudflare 控制台观察容量、读写量、请求量和 CPU 时间，不先建设自有用量仪表盘。
- 暂不显示每人 GB 容量条，不用导出 JSON 的大小冒充数据库真实占用。以后确有需要，再评估按记录数限制。
- 免费版每个请求只有 10 ms CPU。OWASP 推荐强度的 scrypt 或 PBKDF2 在本地实测约 40 至 90 ms，会超出上限，所以密码采用加盐 SHA-256，耗时远低于 1 ms。
  它能避免数据库里直接出现明文，但抵挡不了专业的离线暴力破解。这是自用加朋友内测、坚持免费的取舍；以后若升级 Workers Paid，可改用 scrypt。
- 曾接入 Auth0 Free 托管登录来规避 CPU 限制；考虑到这是自用加朋友的小应用，按 Master Feiii 的决定改回本站自管。

## 分阶段范围

1. `[基础多人使用]` 完成认证验证、迁移、数据隔离、邀请注册、角色创建和基础后台 → verify: 双账号隔离及恢复演练通过。
2. `[全站奖励规则]` 增加有限的经验和星星规则配置 → verify: 历史重算一致、影响提示明确、已解锁成就保留。
3. `[后续候选]` 另行评估音效、公告和每日语录管理 → verify: 先确认具体用途，再决定是否开发。

音效当前通过 Web Audio 合成，没有音频文件库。全站默认音量或启用设置与上传、试听、替换音频是不同范围；后者暂不进入首批任务，任何全站默认设置都应保留用户的静音选择。
